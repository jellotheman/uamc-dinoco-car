# World selection research

Checked 2026-11-05 against a pre-implementation code snapshot. This note records research, not current implementation status; see the [documentation index](../README.md). No simulator was launched during the research.

## What the reference actually does

The [AD README](https://github.com/simonli357/AD/blob/cb73d5ad6a407273e125e53a8b559687431cc6f0/README.md) uses ROS 1/catkin and points to a separate [Simulator repository](https://github.com/simonli357/Simulator). Its instructions run `roslaunch sim_pkg run132.launch`. At Simulator revision `8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816`, [run132.launch](https://github.com/simonli357/Simulator/blob/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816/src/sim_pkg/launch/run132.launch) is **ROS 1 XML**, not Python: it includes `gazebo_ros/launch/empty_world.launch` and passes a fixed `world_name` path to `worlds/world2025.world`, along with paused, sim-time, debug, and GUI settings. Additional included launch files supply objects and vehicle setup. Its [SDF world](https://github.com/simonli357/Simulator/blob/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816/src/sim_pkg/worlds/world2025.world) declares its internal world name as `bfmc_official`.

The reference contains multiple scenario-specific XML launches and worlds. This demonstrates an organizational pattern, not a working ROS 2 Jazzy/Harmonic implementation or a user-selectable argument on that particular `run132.launch`. Its Gazebo Classic plugins, assets, interfaces, and licensing would require a separate compatibility and provenance review before reuse.

## ROS 2 launch arguments versus parameters

In Jazzy, [`DeclareLaunchArgument`](https://github.com/ros2/launch/blob/jazzy/launch/launch/actions/declare_launch_argument.py) declares a launch configuration with optional default and choices; [`LaunchConfiguration` and substitutions](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Intermediate/Launch/Using-Substitutions.rst) resolve it when the launch actions execute. [`IncludeLaunchDescription`](https://github.com/ros2/launch/blob/jazzy/launch/launch/actions/include_launch_description.py) passes launch arguments to an included description. A launch argument selects startup actions and does not automatically become a ROS node parameter; [`launch_ros.actions.Node`](https://github.com/ros2/launch_ros/blob/jazzy/launch_ros/launch_ros/actions/node.py) passes its separate `parameters` values to the launched node.

In UAMC, `bringup/launch/sim.launch.py` includes `sim/launch/vehicle_sim.launch.py` and forwards `gui`, `rviz`, and `gz_extra_args`. The child currently hard-codes the installed `practice.sdf` and starts a custom supervisor; neither declares or forwards a world selector. `--show-args` is useful for confirming declared launch options, but it does not prove an OpaqueFunction's runtime actions or validate an SDF.

A future selector should be declared and described in both public entry points and explicitly forwarded to the included launch. Resolve and validate it before Gazebo or related processes start, while retaining the existing single-session lock, supervised process groups, shutdown hooks and safe command behavior. An already running Gazebo process will not switch worlds merely because a ROS node parameter changes. The [Jazzy ros_gz launch template](https://github.com/gazebosim/ros_gz/blob/jazzy/ros_gz_sim/launch/gz_sim.launch.py.in) exposes a `gz_args` startup argument; UAMC instead uses its own supervisor, so its argument and shutdown behavior must be evaluated on its own terms.

## World identity, assets and bridges

The [SDFormat 1.9 specification](https://sdformat.org/spec/1.9/world/) defines the `<world name="...">` attribute independently of the SDF filename and permits multiple worlds per file. In this repo `practice.sdf` currently declares `practice`; the reference's file is named `world2025.world` but declares `bfmc_official`. File basename and Gazebo world name cannot be assumed interchangeable. For a world-name-dependent service, explicitly obtain or declare the actual SDF name; [Jazzy's `create` source](https://github.com/gazebosim/ros_gz/blob/jazzy/ros_gz_sim/src/create.cpp) is the authority for its `-world` argument and discovery behavior. A simple initial design can require one world per supported SDF.

Gazebo requires the selected world and its referenced models, meshes, and system plugins to be locatable; [Harmonic resource lookup](https://gazebosim.org/api/sim/8/resources.html) documents `GZ_SIM_RESOURCE_PATH` and system plugin search paths. A world needs the physics, user-command, scene, sensor and IMU systems required by the existing vehicle and tests. Match each scenario's vehicle spawn pose to its geometry and confirm the obstacle is in LiDAR coverage. Worlds imported from elsewhere can require assets or Classic-only plugins and are not automatically compatible with Harmonic.

The current bridge YAML explicitly maps fixed Gazebo topics `/clock`, `/camera/image_raw`, `/camera/camera_info`, `/scan`, `/imu/data`, `/joint_states`, `/odometry/wheel` and `/model/uamc/cmd_vel` to stable ROS topics; sensor and model plugins define the latter topic names explicitly. Those names are not intrinsically derived from the filename. World-qualified names such as `/world/<worldname>/control` do depend on the internal name. [Jazzy bridge documentation](https://github.com/gazebosim/ros_gz/blob/jazzy/ros_gz_bridge/README.md) also notes that if Gazebo sees another publisher on `/clock`, it publishes its qualified world clock instead; the default UAMC `/clock` bridge would then need corresponding handling. The same upstream documentation states YAML bridge configuration does not support launch substitutions; dynamic world-qualified bridges therefore need explicit configuration generation or a supported launch-based configuration. Preserve directions, message types, QoS and timestamps rather than silently remapping to mismatched topics.

## Design options

1. **Named, packaged scenarios:** declare a `world` launch argument with a known default and fixed choices; map names to installed SDF paths, actual world names and spawn poses. This gives clear errors and an auditable contract. Add worlds only when their assets and required plugins are packaged and their sensor, bridge, track and safety behavior have been validated.
2. **World file path argument:** allow an explicit file path, validate it and the intended internal world name before starting. This is more flexible for experiments but cannot guarantee required plugins, spawn pose, bridge topics, or sensor compatibility. Avoid arbitrary shell interpolation; the supervisor already receives argument-list values.
3. **Scenario-specific launch wrappers:** follow the reference's separate-launch organization, with each wrapper selecting one packaged configuration and including shared UAMC bringup. This is explicit but has more entry points and must continue to forward the shared safety and GUI options.

These are design choices, not implemented features. First add meaningful non-simulator tests for default selection, argument forwarding, invalid paths or names, and world/bridge consistency. Later validate each world with one supervised simulator session, actual camera and scan delivery, correct TF and clock, and the project's stop and fault tests. No world switching or GUI validation was performed for this research.
