Research snapshot: 2026-11-06. Inspected [AD at cb73d5a](https://github.com/simonli357/AD/tree/cb73d5ad6a407273e125e53a8b559687431cc6f0) and [Simulator at 8ed1260](https://github.com/simonli357/Simulator/tree/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816), including their screenshots. This is a source and image review, not a test run.

## Separate simulator and dashboard

The [AD README](https://github.com/simonli357/AD/blob/cb73d5ad6a407273e125e53a8b559687431cc6f0/README.md) describes a ROS autonomy stack and a PyQt5 dashboard, and directs simulation users to a separate Gazebo-based Simulator. The GUI is also intended for a separate computer during real-car operation. The [Simulator README](https://github.com/simonli357/Simulator/blob/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816/README.md) says its starter code is based on [ECC-BFMC/Simulator](https://github.com/ECC-BFMC/Simulator). It is a customized competition simulator, not evidence of a simulator engine built from scratch. The projects use the ROS 1 catkin workflow. AD recommends Ubuntu 20.04/Noetic, whereas UAMC uses ROS 2 Jazzy and Gazebo Harmonic; these are not drop-in launch files for UAMC.

## Gazebo world

The upstream [Gazebo screenshot](https://github.com/simonli357/Simulator/blob/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816/assets/sim.png) shows an oblique overhead view of a large black miniature-road course with white lines, intersections, crosswalks, roundabout, parking bays, road labels, signs, and several small cars. It depicts the simulated environment, not what the car believes. The [launch used in the AD README](https://github.com/simonli357/Simulator/blob/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816/src/sim_pkg/launch/run132.launch) starts Gazebo with world2025.world, simulation time and GUI enabled; it also spawns a car and includes a ramp, separators and signs. Screenshot content and entities enabled by a particular launch need not be identical.

The [Simulator README](https://github.com/simonli357/Simulator/blob/8ed1260f9dd1baddd1c2acbbfe3bf5d07ca3c816/README.md) describes SDF car and object models, a simulated RealSense D435i, simulated GPS/motor/servo plugins, traffic lights, and a localization bridge with delay and noise. This describes modelled facilities, not proof that each simulated behavior matches the real car. The [official simulator notes](https://github.com/ECC-BFMC/Simulator) recommend the environment for overview, state machine and path planning rather than image processing. [Competition documentation](https://regulation.boschfuturemobility.com/data/whatsprovided.html) recommends integration testing rather than fine tuning due to lower environmental noise than reality.

## AD dashboard

The [dashboard screenshot](https://github.com/simonli357/AD/blob/cb73d5ad6a407273e125e53a8b559687431cc6f0/assets/gui.png) shows a dark interface with a large, labelled top-down track map and points; a lower log and launch controls; and a right-side perspective map/car view with compass, speed and other indicators. Its top-right panel shows calibration text and a grid in that still image; a live camera feed is not demonstrated by that screenshot. The [AD README](https://github.com/simonli357/AD/blob/cb73d5ad6a407273e125e53a8b559687431cc6f0/README.md) states that the PyQt5 GUI can visualize a camera feed, state estimates, planned paths and detected objects, and offers start/stop, replanning, object toggles and node-launch controls. Its described use includes selecting destinations and planning before starting. The screenshot is a representative still, not a guarantee that all features are running at once.

## A useful small UAMC version

UAMC already has Gazebo practice and hairpin scenarios and an RViz view showing its robot, scan, lane and plan; see the [project guide](../guides/guide.md) and [scenario record](../development/scenario-implementation.md). Start with those rather than porting the older simulator or rebuilding the dashboard. A useful first visual setup would put the Gazebo world next to RViz and optionally the camera image: Gazebo answers where the simulated car and obstacle actually are, while RViz shows lane/path and LiDAR information available to the software. Add simple readable arm/fault/obstacle and measured speed indicators only when needed; label simulated truth separately from estimated pose, and represent missing or stale data explicitly. A whole-course map and custom integrated dashboard are optional later enhancements if a concrete debugging need warrants them; the hairpin RViz configuration currently shows local sensors and paths, not a full course map. Validate any plan against actual topic types, timestamps, frames and launch configuration before implementation.

Simulator behavior, fake vehicle readiness and provisional geometry do not establish real-car safety, sensor calibration, stopping distance or physical qualification. The [runbook](../guides/runbook.md) describes the disabled real transport and required bench work.
