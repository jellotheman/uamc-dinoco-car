# UAMC Round 1 implementation plan

> Original implementation specification and acceptance targets. This plan records intended work; see the [documentation index](docs/README.md) for current operation, evidence, and outstanding hardware work.

## Scope and deliverables

**Software handoff.** Deliver the runnable Python ROS 2 Jazzy application for the team's existing, assembled car. Basic physical testing has already been done. Use the team's working firmware, controls, calibration, and test results as starting inputs where available. The handoff includes autonomous lane keeping and obstacle stopping, basic manual RC controls for testing, the hardware integration, the stock Gazebo Harmonic and RViz2 setup, and a short runbook. Use section 13 of the pasted explanation as the development order and the car manual for the stock chassis.

**Team qualification submission.** The competition calls for a **3–5 minute video of the physical car** autonomously following a lane and stopping at an obstacle on a self-built practice track, plus a **1–2 page Technical Design Document**. The team produces these separate competition deliverables, and the Team Leader submits them through Techfest. Software validation logs and measurements can support the team's TDD. See pages 4 and 7 of the competition PDF.

## Reuse and implementation approach

Start each subsystem by checking the team's existing code and firmware, then look for a maintained ROS 2 Jazzy package or vendor driver that fits the interfaces. Prefer configuration and remapping of proven components, then a small adapter, then a targeted port of tested code. Write new code for behavior and integration gaps that remain. Use [AD](https://github.com/simonli357/AD) as an architectural reference and evaluate individual components for reuse where they fit Jazzy, the car, and Round 1. Record upstream versions and provenance, preserve license notices, and check the competition's originality requirements before incorporating a third-party port.

## Shared ROS interfaces

Use packages under `ros2_ws/src` for interfaces and utilities, embedded I/O, description and simulation, perception, localization, planning, control, and bringup. Project ROS nodes use `rclpy`. Use `ament_cmake` with `rosidl` for custom interfaces and Python bindings.

| Interface | Contract |
| --- | --- |
| `/camera/image_raw`, `/camera/camera_info`, `/scan`, `/imu/data` | Standard `Image`, `CameraInfo`, `LaserScan`, and `Imu` with matched timestamps and frames |
| `/odometry/wheel`, `/odometry/filtered` | Standard `Odometry` from measured wheel motion and the local EKF |
| `/perception/lane`, `/planning/path` | Metric `nav_msgs/Path` in rear-axle `base_link`. Preserve the source stamp and publish an empty path on invalid perception |
| `/perception/obstacle`, `/vehicle/status` | Stamped obstacle validity, detection, and bumper clearance. Stamped actuator readiness, E-stop, and fault status |
| `/drive/requested`, `/drive/manual`, `/drive/command` | Autonomous request, manual request, and final command as `AckermannDriveStamped` in m/s and radians. The safety gate selects the input for the launch mode and is the sole publisher of the final command. |
| `/safety/arm`, `/safety/reset`, `/round1/run` | `SetBool` to arm or disarm, `Trigger` to reset a cleared fault at standstill, and a `DriveRound1` action using the configured run speed |

The autonomous action accepts one local goal after arming, reports run state and clearance, and succeeds after an obstacle-triggered stop and measured standstill. Cancellation, disarm, or fault commands zero and ends the run. Recovery requires a deliberate new start. Use sensor-data QoS for raw sensor streams and steady-time watchdogs for command and input loss.

**Manual RC mode.** Add a separate, opt-in manual launch profile for bench and practice use. Reuse the team's existing RC input path if it passes the same mode isolation and fail-safe checks. The ROS gamepad path uses [`joy`](https://github.com/ros-drivers/joystick_drivers/blob/ros2/joy/README.md) and [`joy_teleop`](https://index.ros.org/p/joy_teleop/#jazzy) to map steering and throttle independently to `/drive/manual`. Use configuration first and add a small adapter only if the installed mapping cannot meet the command contract. Support left and right steering at neutral, forward throttle, and return to neutral. Enable capped reverse only after verifying the ESC's reverse behavior. Require arming and a held deadman. The safety gate checks the enable input and command freshness, commands neutral on release or disconnect, and requires neutral and a fresh enable press after reconnect. Keep the hardware E-stop, watchdogs, and actuator limits active. Start disarmed and allow one command source per launch. The qualification launch starts in autonomous mode with manual inputs disabled.

## Section 13 implementation order

1. **Establish the vehicle interface.** Review the existing car's firmware, controls, wiring, and basic test results first. Use a fake transport for automated tests and a motor-disabled profile for initial bringup. Validate manual steering, throttle, and neutral through the shared safety gate before closed-loop autonomy. The car manual identifies an MJX Hyper Go H12Y/H12Y+ with front steering and four driven wheels. Treat the ESP32 as the likely controller. Identify the exact board, ESC variant, existing firmware and transport, wheel-speed source, BNO055 wiring, and power and cutoff paths before enabling actuation. Reuse working firmware if it can report real feedback and pass watchdog tests. If the board is confirmed as an ESP32 and its firmware is unusable, implement a small ESP-IDF firmware over USB serial with versioned, sequenced, checksum-validated commands, calibrated servo and ESC outputs, feedback, and a local timeout that forces the verified safe output. Use the Lenovo webcam over UVC, Slamtec’s C1 driver, and the BNO055 over its verified bus. Real drive remains gated on a working independent E-stop, protected and fused or current-limited power, measured speed feedback, and a passing wheels-lift test. [ESP-IDF PWM and fault handling](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/peripherals/mcpwm.html) · [Slamtec ROS 2 driver](https://github.com/Slamtec/sllidar_ros2)
2. **Match the interfaces in Gazebo.** Build a Xacro/URDF with four wheel joints, two front steering joints, and camera, IMU, and planar LiDAR frames. Start with a provisional 232 mm wheelbase, 165 mm track, and 90 mm tire diameter. Measure the loaded car and sensor mounts before physical calibration. Use a small marked SDF practice track with straight and curved segments and a box at scan height. Bridge clock, sensors, joint states, and wheel odometry. A Python adapter converts speed and steering angle to `Twist` for Gazebo’s stock Ackermann system, sends zero on command timeout, and triggers simulation shutdown if the adapter or bridge exits. Provide `sim.launch.py` and `real.launch.py` through `uamc_bringup`, with RViz2 optional. [Gazebo Ackermann system](https://gazebosim.org/api/sim/8/classgz_1_1sim_1_1systems_1_1AckermannSteering.html) · [Jazzy bridge](https://github.com/gazebosim/ros_gz/blob/jazzy/ros_gz_bridge/README.md)
3. **Achieve lane following.** Use two high-contrast boundary markings on the practice track. Calibrate the camera, undistort the image, and project a near-to-far crop onto the ground plane. Fit both boundaries, check their spacing, and publish their centerline in meters. Track it with pure pursuit, curvature-based speed reduction, and bounded steering and acceleration. Loss of a valid centerline causes a stop.
4. **Add local localization.** Configure `robot_localization` in 2D with measured wheel speed and BNO055 yaw rate. Give the EKF sole ownership of `odom` → `base_link`. Use sensor freshness for the safety decision because the EKF can continue predicting after inputs stop. Keep localization local to the practice track. [EKF configuration](https://github.com/cra-ros-pkg/robot_localization/blob/rolling-devel/params/ekf.yaml)
5. **Add the obstacle stop.** The C1 supplies one horizontal scan plane. Transform returns into `base_link`, check the swept vehicle footprint along the commanded curvature, and measure clearance from the bumper. Use measured latency, conservative braking or coast-down distance, and a positive margin to set the stop envelope. Treat ordinary `+Inf` beams as no return and stale scans, missing transforms, or insufficient forward coverage as faults. Decelerate for a valid obstacle and hold the stop even if it is removed. [C1 specifications](https://www.slamtec.com/en/c1/spec) · [Driver scan handling](https://github.com/Slamtec/sllidar_ros2/blob/main/src/sllidar_node.cpp)
6. **Integrate and document.** Provide a short WSL and Pi runbook for dependency install, `colcon` build and test, launch, calibration, and rosbag2 record and replay. Use the Pi’s SD card for configuration and recordings. Keep sensor recordings out of the repo and hand off measured track results for the team's qualification materials.

## Acceptance checks

- **WSL and simulation.** Build from the Jazzy underlay with `colcon build --symlink-install` and pass `colcon test`. Verify actual camera and scan delivery, TF ownership, steering direction, and topic parity. Start with a 0.30 m/s simulation cap. Require three consecutive runs through straight and curved sections without crossing a boundary, followed by a stationary stop at least 0.10 m from the box. These are project targets.
- **Fault handling.** Inject stale or invalid lane, scan, IMU, wheel feedback, and drive commands. Exercise cancellation, disconnect, restart, and E-stop. Verify zero output, the expected reported fault, and deliberate rearming. Check that an obstacle outside the swept corridor does not trigger a stop and that a scan intersecting the test obstacle does.
- **Manual control.** Verify steering direction and travel with neutral throttle, capped throttle and neutral, and reverse if enabled. Confirm deadman release, disconnect, and reconnect behavior. Verify manual requests have no effect in the autonomous profile.
- **On-car software acceptance.** Use the existing car and build on its basic tests. On the Pi, verify device IDs, calibration, actuator neutral and limits, link-loss behavior, and independent cutoff with the wheels lifted. Measure latency and worst observed stopping distance at the chosen low-speed cap. Repeat the closed-course runs and confirm positive bumper clearance and a stationary hold. Hand the team the software, runbook, and measured results.
